# 仓库守望（dsh-repo-watch）

> **0.0.1 是占位版本**，只用来占住包名。真正的功能在 0.1.0。

给 DSH 装一个**常驻守望**：它盯着你的 GitHub 仓库，**只有真的有人等你时才说一句话**。

## 它解决什么

不是"我的仓库没有反馈"，而是：**我不主动去看的时候，完全不知道这些仓库发生了什么。**

真实案例：

- 一个月前你在别人仓库提的 bug，维护者回了两次、专门跑了取证实验，你没看到；
- 你在另一个仓库提的四条规则被采纳并写进文档，你一个月后才知道。

现有工具（`octobox`、`devhub`、`tj/triage`、`dinghy`）都能解决这个问题，但**都要你主动打开**。这个插件反过来：**它来找你**。

## 和它们的差别

| | octobox | devhub | triage | dinghy | 本项目 |
|---|---|---|---|---|---|
| 主动推送 | ❌ | 仅通知 | ❌ | ❌ | ✅ |
| 独立完成状态 | ✅ | ✅ | ❌ | ❌ | ✅ |
| 自动判断"谁在等我" | 人工 | 人工 | 人工 | ❌ | ✅ |
| 阈值抑制 | 人工 | 人工 | ❌ | ❌ | ✅ |
| 零操作 | ❌ | ❌ | ❌ | ❌ | ✅ |

## 设计要点

**状态机**（借 octobox 的洞察：GitHub 的已读标志不可用，打开即已读，信息永久丢失）：

```
[pending] ──我看过了──> [seen] ──处理完──> [done]
    ↑                                        │
    └──────── 有新活动（重新浮现）────────────┘
```

**推送只认 `* → pending` 的转换**，其余一律静默——没有新转换就一条消息都不发。

## 它推给你的消息长这样

推的是**一条报数**，不是内容倾泻——在手机上两秒能看完，要不要看细节由你决定：

```
有 4 条新消息（来源：GitHub）

· 需要你回复 4 条 — 有人回复了你提的 issue/PR、@ 了你，或请你 review

回复「查看」查看全部明细；「查看 1」只看需要你回复的。
最近一条：awesome-dsh-plugin/awesome-dsh-plugin#15938　Add: two IM channel plugins…（PR）
```

回「查看」之后，会话里给出带原话的明细（同一条只在聊天里展开，不再二次推送）：

```
共 4 条，显示 4 条：

1. awesome-dsh-plugin/awesome-dsh-plugin#15938　Add: two IM channel plugins…
   有人回复了你提的 PR
   fkysly（11-19）：这个 PR 的合并有冲突，我核过后手动并入了 main…
   https://github.com/awesome-dsh-plugin/awesome-dsh-plugin/pull/15938
```

**为什么不直接推明细**：一条推送里塞四条别人的长评论，读起来是负担；而"有几条、各自要什么"才是决定要不要现在处理的信息。

## 没有通道插件时会怎样

> **前置条件**：守望必须先有一个 IM 通道插件（[`dsh-channel-feishu`](https://github.com/Poy-Coder/dsh-channel-feishu) 或 [`dsh-channel-wechat-ilink`](https://github.com/Poy-Coder/dsh-channel-wechat-ilink)）。**没有通道时守望只能被查询，不能推送**——消息留在内存队列里，装上通道之后才会补发。这是设计使然：推送能力来自通道持有的外部连接，宿主插件没有办法往会话里插一条消息。

守望自己不输出消息——它通过**某个通道插件的 `*_send_message` 工具**把消息送进你的聊天（飞书或微信）。所以：

| 情况 | 行为 |
|---|---|
| 装了通道插件 | 走第一个 `*_send_message`；用 `pushTool` 指定就不会被安装顺序影响 |
| 一个通道都没装 | **收不到任何推送**。消息留在内存队列，`repo_watch_status` 显示「推送通道：没有…」和「排队未发：N」，并每小时在宿主日志提示一次；装上通道后自动补发 |
| 队列超过 100 条 | 丢弃最旧的并记日志（防止无通道时无限增长）|

`repo_watch_status` 现在会显示推送通道、排队条数、上次推送时间与结果——「为什么我没收到推送」能从工具里直接回答。

同一个状态里还有一行版本提示：插件每天最多查一次 npm，发现新版本就显示 `新版本：0.5.6 可用（当前 0.5.5）`。**只提醒，不自动更新**——升级要你自己在 DSH 的 Plugins 页做。

## 配置

| 字段 | 默认 | 作用 |
|---|---|---|
| `repos` | 空 = 你所有仓库 | 只监视这些仓库（`owner/name`）|
| `pollMinutes` | 15 | 轮询间隔（最小 1）|
| `notify` | true | 关掉就只记状态、不推送 |
| `pushTool` | 自动 | 指定推送工具；空则自动选第一个 `*_send_message` |
| `quietHours` | `23-8` | 静默时段（本地时间，跨午夜可写 `23-8`）|
| `maxP0PerHour` | 1 | 每小时最多推几条报数 |
| `backfillDays` | 30 | 首次运行往回看多久 |
| `closedLookbackHours` | 24 | 每轮回扫多少小时的关闭事件，用来结案 |
| `recheckForeignThreads` | true | 每轮复核别人仓库里被跟踪的 thread 是否已关闭/合并（上限 30 条）|
| `muteBots` | true | 按发言人抑制机器人 |
| `tokenEnv` | `GITHUB_TOKEN` | 读 token 的环境变量名 |
| `stateFile` | `~/.dsh/repo-watch.json` | 状态文件位置 |

### 两个会让推送“姗姗来迟”的默认值

这两个不是缺陷，是刻意的降噪，但它们会让事件**晚到**。等待前先看这两条：

**`quietHours: 23-8`（静默时段）**

夜里的新事件不会立刻推，而是**压到早上的第一条消息里合并发出**。所以“昨晚有人回复我，今早才收到”是正常的，不是漏了。

关掉静默：`quietHours: ""`。改成自己作息：例如 `quietHours: "1-7"`。

**`maxP0PerHour: 1`（每小时一条报数）**

同一小时里来了多条新事件，只有第一条会立刻推，**其余合并进下一次**（下一次轮询通常 15 分钟后，且受静默时段影响）。所以：

- 事件密集时会出现“我收到一条，但列表里更多”——这是合并，不是漏推；
- 想每条都立刻推：设 `maxP0PerHour: 5`（代价是可能连发多条）。

两个默认值的共同前提是**“报数式推送”**：一条消息只说“有几条、各自要什么”，所以你晚看到时，内容并没有丢，只是聚合了。

## 状态机：为什么 `ack done` 不会自己回来

一条 thread 有三态：`pending`（等你）/ `seen`（看过了）/ `done`（处理完）。

关键规则：**你标的 `done`/`seen` 不会被下一轮轮询覆盖**——判定逻辑（“对方最后说话的不是我”）在对方再开口前一直为真，若每轮都拿它覆盖状态，`done` 只能活一个轮询周期。现在只有 **更新的活动** 才能把 `done` 重新变回 `pending`。

同理，`snooze` 是“先别告诉我”，不是“永远别说”：到期后条目仍留在「等你」列表，并标注「延后已到期，等你处理」。

结案有三条路径：你标 done、仓库内的 issue 被关闭（`closedLookbackHours` 回扫）、别人仓库里你提的 thread 被关闭或合并（`recheckForeignThreads` 复核）。

## 诊断日志

`~/.dsh/repo-watch.log`，JSONL，超过 2 MB 轮转。记录 `push/sent`、`push/skipped`（带原因）、`settled-by-closure`、`settled-elsewhere`。「为什么没收到推送」「为什么这条还挂着」都能从这里回答。

## 三种摘要

| 摘要 | 内容 | 怎么触发 |
|---|---|---|
| `waiting` | 需要你回复或处理的条目——报数推送里说的就是它 | 回「查看」 |
| `quiet` | **不需要你动手、但确实发生了**的事：别人在你订阅的 thread 里讨论、机器人提交等，留 30 天 | 让我「看看其他动静」 |
| `deep` | 在 `waiting` 基础上给出**判断**：类别（缺陷/功能请求/提问/文档）、优先级与理由、以及本仓库里相似的旧 thread（当时是 done 还是 pending） | 排查、决定先做哪个时用 |

### `deep` 是怎么判断的

全部是**可解释的规则**，不是让模型读一遍猜：

- **类别**：标签优先（`bug`/`regression`、`enhancement`/`feature`、`question`、`docs`），没有标签就看标题措辞；判断时会说明用了哪个信号；
- **进展**（看对方最后一句话，从已存的摘录判断，不额外请求）：
  - `−3` 对方说**已修复/已合并/已发布** → 可能只差关掉；
  - `−2` 对方**在推进**（排查/定位/复现/修复中）→ 可以先等；
  - `+2` 对方**在等你补充**（能否提供/麻烦你/需要你）→ 现在轮到你。
- **优先级**（分数 → 高/中/低）：
  - `+3` 提到回归（以前可用）、涉及数据丢失、被请求 review；
  - `+2` 崩溃/无法启动、@ 了你、你提的 thread 有人回复、**已提醒 3 次仍挂着**；
  - `+1` 放置超过 7 天；
  - `-1` 提问/文档类；`-2` 只有编号没有标题；
- **相似**：同仓库、标题共享 **≥2 个**有效词（英文单词 + 中文二元组，去掉“无法/问题/怎么”这类词），最多 3 条，并显示它们当时的状态。

为什么要可解释：**“这条为什么算高优先级”必须有答案**，否则你没法反驳它，也就不会信任它。
